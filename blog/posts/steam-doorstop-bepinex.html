DOORSTOP_INITIALIZED 短路

2026-08-14 Unity Mono · Windows x86/x64 · Doorstop 4.x / BepInEx 6

Doorstop BepInEx Steam IAT

适用范围：Steam 启动的 Unity Mono 游戏，用 UnityDoorstop 在 mono_jit_init_version 处注入托管程序集（BepInEx 是最常见的消费者）。症状是「同一套文件，从 Steam 普通启动不加载，用管理员兼容或绕过 Steam 就能加载」。这通常被当成 ACL / UAC / 写 Program Files 失败，但断点往往在 Doorstop 的环境变量协议上，托管代码根本没执行。

1. 注入模型

Doorstop 不是调试器，也不改 exe。它做成 version.dll / winhttp.dll 的代理，放在游戏根目录。Windows 加载器解析 UnityPlayer.dll 的静态导入时，先搜 exe 所在目录，于是 Doorstop 的 DllEntry 比托管运行时更早上场。

Windows 入口随后做三件事：

  1. fix_cwd()，保证配置和目标程序集按游戏根目录解析。
  2. load_proxy()，把真实系统 DLL 的导出转发出去（旁边通常要有 version_alt.dll / 系统副本）。
  3. 对 UnityPlayer（没有则对 exe）的 IAT 打 GetProcAddress 钩。当游戏去解析 mono_jit_init_version（以及若干 mono_* / il2cpp_init）时，先走到 Doorstop，再调真正的运行时函数。

Mono 路径里，init_mono 在真正的 mono_jit_init_version 返回之后调用 mono_doorstop_bootstrap。引导函数打开 target_assembly（BepInEx 默认是 BepInEx\core\BepInEx.Unity.Mono.Preloader.dll），用 Mono API 加载镜像，反射调用 Doorstop.Entrypoint.Start。BepInEx 的 chainloader、写 BepInEx.cfg、扫 plugins，全部发生在这之后。

因此分层诊断可以直接看文件时间戳：

观察含义
没有新的 verbose doorstop_*.log代理 DLL 没进这个进程（搜路失败、被别的模块抢先加载了系统同名 DLL，或进程根本不是游戏本体）。
有 Doorstop 日志，没有新的 BepInEx/LogOutput.log原生层活着，Entrypoint.Start 没被调用。
LogOutput.log 有新的 Preloader / Chainloader 行Doorstop 已完成，问题在 BepInEx 或插件。

2. 环境变量协议

Doorstop 用进程环境做跨阶段、跨模块的状态，而不是只靠静态变量。和本问题相关的两个名字：

变量谁写谁读语义
DOORSTOP_DISABLE 启动器 / 上一次 Doorstop / 人工 DllEntry / 配置加载之后 非空则整段禁用。官方提供 ignore_disable_switch 忽略它。
DOORSTOP_INITIALIZED mono_doorstop_bootstrap / CoreCLR 引导在真正 invoke 之前 下一次 mono_doorstop_bootstrap 非空则认为已经引导过，直接 return。

config.h 对 ignore_disable_switch 的说明已经点名 Steam：「launchers that break env var isolation」。它只覆盖 DOORSTOP_DISABLE。DOORSTOP_INITIALIZED 走另一条 getenv，不受这个开关约束。

环境会随 CreateProcess 默认继承。因此下面几种情况会把「已初始化」带进一个从未引导过的新进程：

  • Steam 客户端给游戏进程塞了一份被污染的环境块（实测可同时带上 DOORSTOP_DISABLE 和 DOORSTOP_INITIALIZED）。
  • 游戏或插件用 Process.Start 拉起自身，子进程继承父进程环境（上游 #73）。
  • 同目录的 UnityCrashHandler*.exe 也会加载 VERSION.dll；它不是 Mono 进程，但会跑 Doorstop 的 DllEntry。真正要命的是父进程环境，不是 handler 自己有没有 bootstrap。

「管理员就能好」是红鲱鱼。兼容层 RUNASADMIN 走 UAC，子进程不继承 Steam 那份环境，两个变量都消失，引导恢复。UIPI 挡住 overlay 是并列现象，不是 Skipping! 的充要条件。

3. 代理 DLL 与 IAT

和 env 正交的一层是：代理必须成为 UnityPlayer 实际绑定的那个模块。

BepInEx 的 Windows 发行包默认落地 winhttp.dll。Steam overlay / steamclient 经常先加载系统 winhttp.dll。进程里已有同名模块后，游戏目录那份不再参与 UnityPlayer 的导入绑定，Doorstop 整段缺席（连 verbose 日志都没有）。

Doorstop 4.x 的 proxylist.txt 同时列出 VERSION 与 WinHttp 导出。把同一份二进制命名为 version.dll 通常更稳：UnityPlayer 静态导入 VERSION.dll，加载器会绑到 exe 目录。转发真实实现时需要 version_alt.dll（系统 VERSION.dll 的副本）。不要同时再放一份游戏目录 winhttp.dll 去和 overlay 抢。

IAT 钩子本身用「槽里的指针是否等于 &GetProcAddress」匹配。overlay 若先把该槽改成自己的 trampoline，按地址钩会失败。按 OriginalFirstThunk 的导入名钩可以扛住已经改过的 IAT；这是独立问题，和 DOORSTOP_INITIALIZED 短路不是同一处 return。

4. 关键日志

编译带 VERBOSE 的 Doorstop 时，游戏根目录会写出 doorstop_<pid>.log。下面是 Steam 普通启动、开关已经打开、代理也已经是 VERSION.dll 时的典型失败（全文见附件）：

CONFIG: General.enabled = true
CONFIG: General.ignore_disable_switch = true
Doorstop enabled!
Installing IAT hooks
Hooks installed, marking DOORSTOP_DISALBE = TRUE
Got mono_jit_init_version at 097B0000
Starting mono domain "Unity Root Domain"
Overriding mono DLL search path
DOORSTOP_INITIALIZED is set! Skipping!

对应源码是 src/bootstrap.c 里 mono_doorstop_bootstrap 开头的 getenv("DOORSTOP_INITIALIZED")。这条路径在 fopen(target_assembly) 之前就返回，所以不会出现 Opening assembly，BepInEx 侧也不会有新的 Preloader 行。

对照实验：同一构建，提升完整性级别再启动（或从非 Steam 的干净环境启动），同一行变成继续往下走，LogOutput.log 出现 BepInEx 6.x chainloader。差异只有进程环境，不是文件 ACL。

5. 修补

正确语义：ignore_disable_switch 表示「不要信任从父进程继承来的 Doorstop 控制变量」。它应当同时作用于 DOORSTOP_DISABLE 和 DOORSTOP_INITIALIZED。本进程内的防重入改用静态标志，避免依赖一块会被 CreateProcess 复制的环境。

实现（已提交 NeighTools/UnityDoorstop#109）：

位置行为
src/windows/entrypoint.c · DllEntry，load_config() 之后 若 config.ignore_disabled_env，SetEnvironmentVariableW 清掉 DOORSTOP_INITIALIZED 与 DOORSTOP_DISABLE。
src/nix/entrypoint.c · doorstop_ctor 对等的 unsetenv。Steam Proton / 原生 Linux 是同一类继承。
src/bootstrap.c · mono_doorstop_bootstrap 静态 doorstop_bootstrapped 处理进程内二次进入；仅当开关为关时，才把已存在的 DOORSTOP_INITIALIZED 当成硬跳过。

上游默认 ignore_disable_switch 仍是 false，避免改变非 Steam、主动用 DOORSTOP_DISABLE 的流程。Steam 发行或自重启场景在 ini 里打开开关即可同时覆盖两个变量。

游戏根目录最小配置：

[General]
enabled = true
target_assembly = BepInEx\core\BepInEx.Unity.Mono.Preloader.dll
ignore_disable_switch = true

BepInEx 发行层（把 Windows 包默认打成 version.dll、把开关默认打开）属于产品策略，不是这次短路的充要修复。按 BepInEx 的贡献约定，改默认行为应先开 issue，本文不把它当成补丁本体。

6. 验证

  1. 从 Steam 以 Medium 完整性启动（不要 RUNASADMIN）。
  2. verbose 日志应出现 Cleared inherited DOORSTOP_INITIALIZED / DOORSTOP_DISABLE，随后 Opening assembly，不能再停在 Skipping!。
  3. BepInEx/LogOutput.log 的修改时间对应当次启动，并含 Preloader / Chainloader 行。
  4. 回归：显式设置 ignore_disable_switch = false 且父进程带上 DOORSTOP_INITIALIZED，仍应跳过——确认没有把防重入整段拆掉。
