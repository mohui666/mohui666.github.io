Koozhan 中转站避雷：连续 429 把 Codex 干碎了

2026-08-18 个人实测 · 长 Agent 工作流

Koozhan 中转站 Codex 429 避雷

最近拿 Koozhan 跑 Codex，给我的体验只能说：真他妈离谱。

这不是偶尔弹一次 429，也不是我开几十个并发把接口狠狠干爆了。就是一个正常的 Coding Agent 工作流：改代码、提交、push、检查 GitHub Actions、准备重建 Release。

然后同一轮任务里，短时间连续给我来了至少三次：

exceeded retry limit, last status: 429 Too Many Requests

三个不同的 request id：

e6e954dc-7d25-4bb0-8769-6f8a55436ca5
63d05a44-ae3a-4b56-8fc4-0fc73c4072af
411099fa-e8b6-4f3f-94be-ede902d80842

这不是“一次偶发 429”

第一次报错时，Codex 正准备提交；恢复之后 commit 建好了。接着准备 push，又来一次 429。好不容易 push 到 origin/master，准备继续检查 Actions、标签和本地产物，第三次 429 又把执行链干断。

整个流程差不多就是：

Codex：我先提交代码。
中转：429。

Codex：提交好了，我 push。
中转：429。

Codex：push 好了，我继续检查 Actions / Release。
中转：又他妈 429。

客户端：exceeded retry limit

看到这里我就一个问题：

你这中转到底中转了个鸡巴？

我为什么直接说它是“黑心商家”

这是我基于这次实际付费体验给出的主观评价：黑心商家。

我掏钱用中转，不就是图一个省心吗？上游账号、渠道容量、RPM、TPM、线路切换、调度这些东西，本来就是中转服务应该替用户处理的。

结果钱照样花，真正跑任务的时候用户看到的是：

429
retry
429
retry
exceeded retry limit

然后烂摊子还是用户自己收拾。

我还得重新确认：

  • commit 到底有没有成功；
  • push 到底有没有完成；
  • GitHub Actions 有没有触发；
  • 标签有没有推上去；
  • Release 做到哪一步了；
  • Agent 上一轮执行状态还能不能接着用。

我花钱是来跑 Coding Agent 的，不是来玩《429 状态恢复模拟器》的。

对 Agent 用户尤其恶心

普通聊天偶尔 429 一下，你重新生成一次，损失可能没那么大。

但 Agent 不一样。它可能已经读了几十个文件、改了代码、跑了测试、积累了一大坨上下文，甚至已经执行了一部分具有外部状态的操作。

这时候中间突然一句：

exceeded retry limit

不是简单的“再问一遍”就完事了。你得先检查半天当前状态，避免重复提交、重复发 Release、漏跑 CI，或者把已经成功的步骤当成失败重新执行。

所以对长 Agent 工作流来说，稳定性不是“体验加分项”，而是最基础的服务指标。

“API 偶尔 429 很正常”也别拿来洗

API 偶发限流当然正常，我也不是第一次用 API。

但我这里是：同一个任务、短时间内、连续三个不同 request id、每次都已经自动重试到彻底失败。

至于后台到底是上游账号爆了、渠道容量不足、RPM/TPM 不够、调度没切过去，还是别的原因，我不知道，也不会编一个内部原因替它定罪。

但这根本不是付费用户应该操心的问题。

你是中转商，你收的就是这个钱。用户最后只看一件事：请求到底能不能稳定跑完。

更恶心的是：我这边余额还退不了

连续 429 把 Agent 工作流狠狠干断以后，我想着既然这服务我已经不敢继续拿来跑长任务，那剩下的钱退掉算了。

结果我这边实际遇到的情况是：剩余余额无法退款。

这一下就真的把我恶心到了。

服务稳定性已经差到让我不想继续用，长任务连续 429 → retry → exceeded retry limit；用户想退出，钱又拿不回来。

能充值，不能退款；能收钱，服务炸了以后余额还得继续烂在里面。

我不知道它内部对退款到底怎么规定，也不替它编理由。我只写我自己的实际结果：我想退，我这边退不了。

你要是真对自己的服务有信心，用户觉得不好用要走，把没消费掉的余额退掉不就完事了？现在是 429 把人赶走，余额又把人拴住。

线路我不敢用了，钱我还拿不回来。就这体验，我说一句黑心商家一点不过分。

我的结论

如果只是短聊天、临时问几个问题，也许你自己试试就完事。

但如果你的用途是：

  • Codex / Coding Agent；
  • 长上下文编程；
  • 多轮工具调用；
  • 自动化工作流；
  • CI / Release 操作；
  • 需要连续跑很久的任务；

我的建议就是：先小额测试，别看便宜就往里面狠狠干一大笔余额。

尤其是现在我自己还碰到了余额无法退款。别最后省几毛 Token 钱，既要花十几分钟甚至更久收拾 Agent 中断现场，剩余的钱还退不回来。

我个人实测后的评价：Koozhan 这次的表现就是黑心中转，体验司马。

连续 429、三个 request id、全部 retry limit，以及我这边后续无法退款，都是我这次实际使用中遇到的情况。
